Beginner Guide: Frugal EV Opinion Simulator MVP

How to run the API, test live LLM mode, and read the results

1 What this guide is for

This guide explains how to use the new Frugal EV Opinion Simulator MVP in Oransim. It assumes you are a beginner and want step-by-step commands plus a plain-English explanation of the output.

The simulator answers this question:

If we show a low-cost electric vehicle concept to different buyer segments, what objections, positive hooks, and purchase-intent scores might appear?

It is useful for early market-entry exploration. It is not a replacement for real surveys, interviews, field trials, or sales data.

2 What was added

The MVP added these pieces:

Area File Purpose
Niche registry data/niches.json Adds frugal_ev as a recognized market niche
Personas data/personas/frugal_ev_personas.json Defines five buyer segments
Concepts data/concepts/frugal_ev_concepts.json Defines three EV offers to test
Schema backend/oransim/schemas/frugal_ev_opinion.py Defines the request and response shape
LLM prompt backend/oransim/agents/frugal_ev_persona_prompt.py Asks the LLM to simulate one persona reaction
API router backend/oransim/api_routers/frugal_ev.py Adds the simulator endpoint
App wiring backend/oransim/api.py Registers the new router

The endpoint is:

POST /api/frugal-ev/simulate

3 Start in the right folder

Open PowerShell and go to the local Oransim clone:

cd "D:\OneDrive - University of Leeds\EV-Infra\EV_modelling\studies\oransim"

Check that you are in the right folder:

Get-ChildItem backend\oransim\api.py
Get-ChildItem data\personas\frugal_ev_personas.json
Get-ChildItem data\concepts\frugal_ev_concepts.json

If those three commands show files, you are in the correct place.

4 Choose mock mode or live LLM mode

You can run the simulator in two modes.

4.1 Option A: Mock mode

Mock mode does not call an external LLM. It is fast, free, and deterministic. Use it first to make sure the API works.

$env:PYTHONPATH = "backend"
$env:LLM_MODE = "mock"
$env:POP_SIZE = "10000"
$env:SOUL_POOL_N = "5"

4.2 Option B: Live LLM mode

Live LLM mode calls your configured provider. Use it when you want model-written persona reactions.

Oransim reads environment variables from the process. It does not auto-load .env by itself. If your API key and model are in .env, load them into the current PowerShell session:

Get-Content ".env" | ForEach-Object {
  $line = $_.Trim()
  if (-not $line -or $line.StartsWith("#") -or ($line -notmatch "=")) { return }

  $parts = $line -split "=", 2
  $key = $parts[0].Trim()
  $value = $parts[1].Trim()

  if (($value.StartsWith('"') -and $value.EndsWith('"')) -or
      ($value.StartsWith("'") -and $value.EndsWith("'"))) {
    $value = $value.Substring(1, $value.Length - 2)
  }

  [Environment]::SetEnvironmentVariable($key, $value, "Process")
}

$env:PYTHONPATH = "backend"
$env:LLM_MODE = "api"
$env:POP_SIZE = "10000"
$env:SOUL_POOL_N = "5"

If you previously saw connection errors to 127.0.0.1:9, clear dead proxy settings in the same PowerShell session:

$env:HTTP_PROXY = ""
$env:HTTPS_PROXY = ""
$env:ALL_PROXY = ""
$env:http_proxy = ""
$env:https_proxy = ""
$env:all_proxy = ""

Check the LLM configuration without printing your key:

python -c "from oransim.agents.soul_llm import llm_available, llm_info; info=llm_info(); print({'available': llm_available(), 'mode': info['mode'], 'provider': info['provider'], 'model': info['model'], 'api_key_set': info['api_key_set']})"

You want:

'available': True
'mode': 'api'
'api_key_set': True

5 Start the API server

Run:

python -m uvicorn oransim.api:app --host 127.0.0.1 --port 8000

Leave this PowerShell window open. It is now running the API server.

Open a second PowerShell window for the API requests.

6 Check that the server is alive

In the second PowerShell window:

Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/health"

The important part is:

status : ok

If this fails, the server is not running or the port is different.

8 Worked example: what this PowerShell request does

This section explains the first request line by line. The full request is:

$body = @{
  concept_id = "frugal_ev_city_9999"
  target_market = "UK"
} | ConvertTo-Json

$result = Invoke-RestMethod `
  -Uri "http://127.0.0.1:8000/api/frugal-ev/simulate" `
  -Method Post `
  -ContentType "application/json" `
  -Body $body

$result

8.1 Step 1: Create the request body

This part:

$body = @{
  concept_id = "frugal_ev_city_9999"
  target_market = "UK"
} | ConvertTo-Json

creates a small JSON message. You can inspect it:

$body

It should look like this:

{
  "concept_id": "frugal_ev_city_9999",
  "target_market": "UK"
}

The two fields mean:

Field Value Meaning
concept_id frugal_ev_city_9999 Use the GBP 9,999 city EV concept
target_market UK Label the report as a UK market simulation

The concept_id must match one of the IDs in:

data/concepts/frugal_ev_concepts.json

For example, frugal_ev_city_9999 points to a concept with:

{
  "concept_id": "frugal_ev_city_9999",
  "name": "GBP 9,999 City EV",
  "price": 9999,
  "range_km": 180,
  "battery_warranty_years": 5
}

8.2 Step 2: Send the request to the API

This part:

$result = Invoke-RestMethod `
  -Uri "http://127.0.0.1:8000/api/frugal-ev/simulate" `
  -Method Post `
  -ContentType "application/json" `
  -Body $body

sends the JSON body to your local Oransim server.

The pieces mean:

Part Meaning
Invoke-RestMethod PowerShell command for calling an HTTP API
-Uri "http://127.0.0.1:8000/api/frugal-ev/simulate" The local endpoint you are calling
-Method Post Send data to the API, rather than just reading a page
-ContentType "application/json" Tell the server the body is JSON
-Body $body Send the JSON created in Step 1
$result = ... Store the API response in the $result variable

127.0.0.1 means “this computer”. Port 8000 is where Uvicorn is running the Oransim API.

8.3 Step 3: What happens inside Oransim

When the request reaches Oransim, the backend follows this path:

PowerShell request
  -> backend/oransim/api.py
  -> backend/oransim/api_routers/frugal_ev.py
  -> data/concepts/frugal_ev_concepts.json
  -> data/personas/frugal_ev_personas.json
  -> backend/oransim/agents/frugal_ev_persona_prompt.py
  -> LLM provider, or deterministic mock fallback
  -> backend/oransim/schemas/frugal_ev_opinion.py
  -> JSON response returned to PowerShell

More concretely:

  1. api.py has registered the frugal EV router.
  2. api_routers/frugal_ev.py receives your request.
  3. It looks up frugal_ev_city_9999 in the concepts JSON file.
  4. Because you did not specify segments, it loads all five default personas: urban_commuter, first_time_car_buyer, delivery_driver, rural_budget_family, and ev_skeptic.
  5. For each persona, it builds a prompt containing:
    • the person’s segment,
    • income level,
    • main need,
    • concerns,
    • decision drivers,
    • EV price,
    • EV range,
    • warranty,
    • features,
    • marketing message.
  6. If LLM_MODE=api and your key is available, it sends that prompt to the configured LLM provider.
  7. If live LLM mode is not available, it uses the deterministic mock fallback.
  8. It validates each persona result with the Pydantic schema.
  9. It computes the overall score, strongest segments, weakest segments, objection themes, message hooks, and verdict.

8.4 Step 4: Print the result

This final line:

$result

prints the response stored in $result.

For a live LLM run, you may see output shaped like this:

concept_name: GBP 9,999 City EV
target_market: UK
overall_acceptance_score: 0.700
strongest_segments: {urban_commuter, first_time_car_buyer}
weakest_segments: {rural_budget_family, ev_skeptic}
verdict: Promising for urban_commuter...

The exact values can vary in live LLM mode. Mock mode is deterministic.

8.5 Step 5: Inspect the most important part

The most important part of the result is:

$result.segment_opinions

Each row is one buyer segment’s simulated reaction. For example:

segment: urban_commuter
purchase_intent_score: 0.70
trust_score: 0.60
price_acceptance_score: 0.90
range_confidence_score: 0.80
charging_confidence_score: 0.40
top_positive_reason: Unbeatable price for an EV with very low running costs
top_objection: No dedicated home charging available

Read this as:

  • the city commuter likes the low price,
  • the price is accepted strongly,
  • charging is still the weak point,
  • the next evidence or product feature should address charging access.

8.6 Step 6: Turn the object into a table

PowerShell prints nested JSON objects awkwardly. Use this table command:

$result.segment_opinions |
  Select-Object segment,
                purchase_intent_score,
                trust_score,
                price_acceptance_score,
                range_confidence_score,
                charging_confidence_score,
                top_objection |
  Format-Table -Wrap

This gives you a readable segment-by-segment comparison.

8.7 Step 7: Ask “why did the model produce this?”

The result is generated from the combination of concept attributes and persona attributes.

For frugal_ev_city_9999, the concept has:

  • very low price,
  • short city-car range,
  • five-year battery warranty,
  • compact daily-trip positioning.

For urban_commuter, the persona has:

  • city use case,
  • short daily trips,
  • concerns about parking and charging,
  • interest in low running cost and compact size.

That is why a typical output may say:

  • positive reason: low running cost and city convenience,
  • objection: parking or charging access,
  • likely social comment: “tempting, but where do I charge it?”

The API is not searching the internet and not using real survey data in this MVP. It is producing an LLM-based structured simulation from the JSON concept and persona definitions.

8.8 Step 8: Save the complete object before interpreting it

Always save the full response before summarizing:

$result | ConvertTo-Json -Depth 10 |
  Set-Content "frugal_ev_city_9999_result.json" -Encoding UTF8

This protects you from losing details that PowerShell may hide in the default screen output.

9 Save the result to a JSON file

Saving the result makes it easier to inspect and compare later.

$result | ConvertTo-Json -Depth 10 |
  Set-Content "frugal_ev_city_9999_result.json" -Encoding UTF8

Open the file:

notepad frugal_ev_city_9999_result.json

10 Understand the response

10.1 Top-level fields

Field Meaning How to read it
concept_name Name of the EV concept tested Confirms which offer was simulated
target_market Market label from your request Usually UK unless you changed it
overall_acceptance_score Average purchase intent across returned segments Higher means stronger simulated demand
segment_opinions One detailed reaction per buyer segment This is the most important section
strongest_segments Top two segments by purchase intent Best early target segments
weakest_segments Bottom two segments by purchase intent Segments needing product/message changes
top_objection_themes Main objections from the personas Use these to improve the concept
top_message_hooks Strongest positive reasons Use these in messaging hypotheses
verdict Short summary sentence Quick headline only; inspect details too

10.2 Score fields inside each segment

Each item in segment_opinions has these scores:

Score Range Meaning
purchase_intent_score 0 to 1 How likely this segment is to consider buying
trust_score 0 to 1 How much they trust the offer, brand, or proof
price_acceptance_score 0 to 1 Whether the price feels acceptable
range_confidence_score 0 to 1 Whether the range feels enough
charging_confidence_score 0 to 1 Whether charging feels practical

Simple interpretation:

Score band Meaning
0.00 to 0.39 Weak
0.40 to 0.59 Mixed
0.60 to 0.79 Promising
0.80 to 1.00 Strong

Do not over-interpret tiny differences. A score of 0.62 versus 0.65 is not a meaningful ranking by itself. Look at the reasons and objections.

10.3 Text fields inside each segment

Field Meaning How to use it
top_positive_reason Best reason this segment likes the concept Turn into message hooks
top_objection Biggest blocker Turn into product or evidence requirements
what_would_change_my_mind What would make the segment more positive Use for follow-up experiments
likely_social_comment Plausible public comment Useful for qualitative interpretation

13 Compare the three EV concepts

The MVP includes three concepts:

concept_id Offer
frugal_ev_city_9999 GBP 9,999 city EV
frugal_ev_family_14999 GBP 14,999 family EV
frugal_ev_subscription Battery subscription EV

Run all three in mock mode or live mode:

$concepts = @(
  "frugal_ev_city_9999",
  "frugal_ev_family_14999",
  "frugal_ev_subscription"
)

$comparison = foreach ($concept in $concepts) {
  $body = @{
    concept_id = $concept
    target_market = "UK"
  } | ConvertTo-Json

  $r = Invoke-RestMethod `
    -Uri "http://127.0.0.1:8000/api/frugal-ev/simulate" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body

  [pscustomobject]@{
    concept_id = $concept
    concept_name = $r.concept_name
    overall_acceptance_score = $r.overall_acceptance_score
    strongest_segments = ($r.strongest_segments -join ", ")
    weakest_segments = ($r.weakest_segments -join ", ")
  }
}

$comparison | Format-Table

Save the comparison:

$comparison | Export-Csv "frugal_ev_concept_comparison.csv" -NoTypeInformation

14 What a good result looks like

A useful result is not just a high score. A useful result has:

  1. Clear strongest segments.
  2. Clear weakest segments.
  3. Objections that make practical sense.
  4. Message hooks that connect to the concept.
  5. No missing or empty text fields.
  6. Scores between 0 and 1.

For example, if urban_commuter is strong but rural_budget_family is weak, that is plausible for a short-range city EV. It suggests the product may be a city-first offer, not a universal family-car replacement.

15 How to check if live LLM mode really ran

Live mode should produce more varied, natural language than mock mode.

Also run:

python -c "from oransim.agents.soul_llm import llm_available, llm_info; print(llm_available()); print(llm_info())"

Expected:

True
{'mode': 'api', ... 'api_key_set': True}

If llm_available() is False, Oransim will use the deterministic fallback.

16 Troubleshooting

16.1 llm_available() is false

Check:

$env:LLM_MODE
$env:LLM_PROVIDER
$env:LLM_MODEL

Do not print your API key. Check only whether it exists:

[bool]$env:LLM_API_KEY
[bool]$env:OPENAI_API_KEY

For OpenAI-compatible providers, one of those should be True.

16.2 API call fails with connection refused to 127.0.0.1:9

Clear proxy variables:

$env:HTTP_PROXY = ""
$env:HTTPS_PROXY = ""
$env:ALL_PROXY = ""
$env:http_proxy = ""
$env:https_proxy = ""
$env:all_proxy = ""

Then restart the server.

16.3 The server starts slowly

Oransim bootstraps a synthetic population and runtime state. For beginner testing, use:

$env:POP_SIZE = "10000"
$env:SOUL_POOL_N = "5"

This is much lighter than the default.

16.4 The terminal shows the pound sign strangely

On some Windows terminals, the GBP symbol may display with the wrong glyph. The underlying JSON file uses the correct Unicode value. This is a terminal encoding display issue, not a simulator logic issue.

16.5 The result is valid but looks too generic

Try live LLM mode instead of mock mode. Mock mode is deterministic and designed for testing, not realism.

16.6 The live call is expensive or slow

Start with one segment:

{
  "concept_id": "frugal_ev_city_9999",
  "target_market": "UK",
  "segments": ["urban_commuter"]
}

Then run all five segments only when you are satisfied the setup works.

18 Suggested workflow for your analysis

Use this order:

  1. Run mock mode for all three concepts.
  2. Compare overall scores and strongest/weakest segments.
  3. Pick the best concept and run live LLM mode for one segment.
  4. If the live output looks sensible, run live mode for all five segments.
  5. Save the JSON output for each concept.
  6. Summarize:
    • best concept,
    • strongest buyer segment,
    • weakest buyer segment,
    • top three objections,
    • top three message hooks,
    • what product change should be tested next.

19 What not to claim

Do not claim:

  • “The market will buy this car.”
  • “This is survey evidence.”
  • “This proves demand.”

Safer wording:

  • “The simulation suggests this concept may be more promising for urban commuters than rural budget families.”
  • “The main simulated blocker is charging access.”
  • “The next real-world test should validate whether this objection appears in interviews or survey responses.”
